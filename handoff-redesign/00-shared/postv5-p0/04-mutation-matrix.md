## P0 #4 ⊕ #9-1 — Per-action mutation + security invariant matrix（24 actions, SINGLE table）

**目的**: postv5 で client reducer (`src/store/reducer.ts`) が今 enforce している SoD・precondition・append-only audit を **server 側へ昇格** し、24 個の `StoreAction` を 1 対 1 で REST endpoint にマップする。各 action 行が「誰が（= token 由来の `session_operator_id` + body 由来で検証された `effective_actor_id` persona）・どの object に・どの prior state から・どの SoD 制約のもとで・どう遷移し・何を監査に残し・client がどう pessimistic に refetch するか」を 1 表で固定する。これが server 実装 + server test の SSOT。

> **right-sizing 宣言**: server は better-sqlite3 + 単一 process Node API（postv5 全体方針）。本 contract は **enforcement を real にする** だけで、production hardening（rate limit / CSRF token / RBAC engine / role-permission DB / IdP / 監査 WORM 保持）は **入れない**。identity は **operator≠persona の dual-identity signed token** で十分。verified token（header `X-Operator-Token`、HMAC-SHA256 署名、payload = `operator_id.issued_at.expires_at.jti`、単一 env secret `BOAI_SESSION_SECRET`）が `session_operator_id`（= 実際の operator）を確定し、request body の `{ actorId }` は `effective_actor_id`（= persona、`allowed_actors` = seed 済 `actors` table 全行 = 3 operational + ≥2 governance = 5 actors に対し server 検証）だけを設定する。**body actorId は `session_operator_id` を絶対に変えない**。これは「operator を token に固定し、persona を body の検証付き actorId に限定する」という今回の中核 invariant を成立させるための最小手段で、それ以上ではない。詳細は末尾「Right-sizing notes」。

> **⚠ live SoD は identity-based であって role-based ではない（contract 全体の前提）**: 現 reducer は **どの action にも `actor.role` 判定を持たない**（`grep -n role src/store/reducer.ts` は audit ラベル用の `roleLabel(actor.role)` `reducer.ts:56` と コメント `:211` のみ。`if (actor.role !== …)` guard は 1 件も無い）。live の SoD は **(a) 自己承認禁止 = `isSelfApproval`（identity equality, `reducer.ts:74-76`）と (b) 裁定者一致 = `currentActorId===escalation.to`（identity equality, `reducer.ts:144`）の 2 つの identity 制約**で成立しており、role に依存しない。デモで「入力者が承認できない／業務責任者だけが裁定する」ように見えるのは、3 actor が 1 role ずつ持つ seed 構成（`actors.ts:17-21`）と escalate 時の `to:'actor-approver'` 固定（`CaseDetailV2.tsx:236`）の**副次的な整合**であって、reducer が role を強制しているからではない。
> 一部 UI hook（`useCanReverse` `hooks.ts:156-164` の `by !== 'checker'`、`by` は `actor?.role === 'inputter' ? 'input' : 'checker'` `CaseDetailV2.tsx:152` 由来）が role めいた先回り gate を持つが、これは **client 表示 gate であり authority ではない**（§C 参照）。したがって本 contract は **24 operational mutation に per-action の role→endpoint 認可（RBAC）を server invariant として課さない**。operational role（inputter / checker / business-approver）の「誰が」の真実源は **identity-SoD（自己承認禁止 + 裁定者一致）+ prior-state の 2 制約のみ**であり、operational mutation 行には role 認可列を置かない（過去版にあった 24×3 role 認可表は live に対応する enforce が無く misleading なため削除した。理由は末尾「Right-sizing notes」参照）。
>
> **⚠ 唯一の role gate = governance boundary（SD-2、restore）**: 上記の「per-action role gate は無い」は **operational role に対してのみ** の言明である。それとは別に、**governance role は READ-ONLY** であり、server は **本表 24 mutation endpoint すべてを governance role に対して REJECT する**（governance は監査・統制の閲覧専用）。これは fine-grained な per-action RBAC ではなく **単一の governance-boundary gate**（「governance は mutate できない」1 本）で、24 mutation に一律適用される唯一の role 認可である。逆に governance-only READ endpoint（`GET /api/audit-events`・model-governance reads・config-approvals reads）は governance role に gate され、inputter / checker / business-approver は endpoint で reject される（この READ 認可は別 contract で扱い、本表は mutation 側のみを SSOT とする）。詳細は末尾「Right-sizing notes」。

> object-scope 規約（下表 scope 列の語）:
> - **存在**: 対象 id が dict に在ること。無ければ `denialReason==='NOT_FOUND'`（reducer は `if (!cur) return state`、例 `reducer.ts:85,107,119,131,142,170,199,212,219,228,251,261,268,279,297`）。**object-level IDOR**（他 actor の object を直 ID で触る）も同じく `denialReason==='NOT_FOUND'` で reject し、existence-hiding として **HTTP 404** を返す（「権限なし」と「不在」を区別しない）。これは default 403 の唯一の例外。
> - **id 重複 no-op**: `case/create` のみ id 既存で冪等 no-op（`reducer.ts:181`）→ server は `CONFLICT`（既存）か 200 冪等のいずれか（OPEN D-2）。
>
> **VALIDATION denialReason（P1a 実装時追加、FK guard）**: postv5 schema は live reducer に無い DB FK を持つ（`escalations.escalated_to`→actors / `cases.workflow_id`→workflows）。よって `case/escalate`（#5）の `to` が未知 actor、`case/create`（#11）の `workflowId` が未知 workflow の場合、生 SQLite FOREIGN KEY error を errorSanitizer の opaque 500 に落とさず **`denialReason='VALIDATION'`（HTTP 403）** で clean に reject する（reducer は任意 string を受けていた、`reducer.ts:131-136`）。`#5` の denialReason 集合に `VALIDATION`（未知 to）、`#11` に `VALIDATION`（未知 workflowId）を追加。denialReason enum の真実源は server `denial.ts`（`VALIDATION` を含む、SD-4）。

### Open decisions

- **D-1 identity 機構（RATIFIED, SD-1）**: server identity は **operator≠persona の dual-identity signed token**（confirmed）。
  - 確定: **`session_operator_id`** = header `X-Operator-Token`（HMAC-SHA256 署名、payload `operator_id.issued_at.expires_at.jti`、env secret `BOAI_SESSION_SECRET`、expiry 30 min、replay reject = in-memory `Set<jti>`）から確定し body では不変。**`effective_actor_id`** = request body `{ actorId }` を **`allowed_actors`（= seed 済 `actors` table 全行 = 3 operational + ≥2 governance = 5 actors）に対し検証**した persona（live const `DEMO_ACTORS` = 3 operational は不変、governance actor は DB `actors` 行として追加。governance actorId は validation を通過するが governance role が mutation を reject する＝governance-boundary test が到達可能）。operator login/issuer は **`POST /api/session/operator`**（2 demo operator op-demo-1 / op-demo-2 は CODE CONSTANT、DB table ではない）。persona 切替の dedicated server endpoint は **無い**（client state + per-write body、UI switcher は 3 operational のみ）。
  - rationale: 「operator を token に固定、persona を body の検証付き actorId に限定」という中核 invariant（T-OPERATOR-IMMUTABLE / T-PERSONA-VALIDATED）を成立させる最小手段。OAuth/JWT issuer/IdP は demo に過剰。reversibility: 高（後で cookie session / 完全 JWT に差替え可、endpoint 契約は不変）。
  - rejected alternative: 単一 `X-Actor-Id` header + body actorId で session を切替える single-identity 案、および dedicated `POST /session/switch` / `POST /session/actor` の server switch endpoint（dual-ID model 採用により drop）。
- **D-2 `case/create` の id 採番と重複時挙動**: client 採番 `CASE-MANUAL-NNN`（`CaseDraftV2.tsx:38-39`）を server 採番へ移譲するか。
  - 推奨 default: **server 採番**（並行起票の id 衝突回避）+ 重複 id POST は **冪等 200**（reducer の no-op 思想に整合, `reducer.ts:181`）。
  - rationale: client 採番は単一タブ前提で multi-actor server では衝突する。reversibility: 中（client の id 生成削除 + response の採番 id 使用に変更, UX flow 不変）。T-DUP(#11) はこの決定に従い `CONFLICT` か 200 のどちらを assert するかを確定させる。
- **D-3 approve/forward/proposal/promotion 系の audit 欠落**: 現 reducer は `case/approve`/`reverse`/`escalate`/`sendback`/`create`/`reprocess`/`resolveEscalation`/`emergencyStop`/`resume` のみ audit append し、**`case/assign`・proposal 4 種・agent promotion 3 種・notification 2 種は audit を生まない**（本表 audit 列 `—`、live 準拠）。
  - 推奨 default: **postv5 では live 準拠（audit 列 `—` のまま）** とし、「手順承認・設定承認を監査に残す」拡張は別 contract に切る。**ただし `—` 集合が意図的であることは T-NO-AUDIT で enforce する**（assert なき `—` 記述は regression で silently 破れるため、negative test で固定）。
  - rationale: 本 contract の scope は「既存 invariant の server 昇格」。audit 範囲拡張は新規 product 決定で、混ぜると scope creep。ただし regulatory reviewer は「承認系が監査に残らない」を問題視し得る → **flag として明示**。reversibility: 高（`logEvent` 呼出し追加のみ, `reducer.ts:48-67`）。
- **D-4 `store/hydrate` / `store/reset` の server 化**: multi-tab 同期 + reset を server 真実源でどう扱うか。
  - 推奨 default: **server endpoint 化しない**（hydrate は「server refetch」に置換）。**P0 の full DB reset は CLI `db:reset-demo` のみ**（default disabled、env-gated、HTTP なし、全 migration 再適用）。HTTP `POST /api/admin/reset` は **OUT-OF-P0**（admin/system role、governance は READ-ONLY ゆえ不可）。いずれも本表対象外。
  - rationale: client state 管理 action で mutation invariant の対象外。reversibility: 高。
- **D-5 denial の HTTP status 割当（RATIFIED, SD-4 = enum is truth）**: 拒否 response は **非 2xx + `{ ok:false, denialReason: <ENUM>, message }`** とし、識別は body の `denialReason` enum で行う。
  - 確定: default は **HTTP 403**（authz / SoD / precondition の denial）、**HTTP 404 は IDOR existence-hiding のみ**（`denialReason==='NOT_FOUND'`）。`denialReason` が機械可読の真実源で、**T-* test は `denialReason` を assert**（bare HTTP code は assert しない）。
  - rationale: 細かい 4xx 分割（422 等）は presentation polish であって、どの invariant も falsifiable にするのに不要（enum 1 つで全 control を区別できる）。mapping 表を維持する保守コストを避けるため **contract column / decision としては持たない**。NOT_FOUND（不在 + IDOR）だけは REST 慣習上 404 を返すが、これも `denialReason==='NOT_FOUND'` を真実源とする。
  - rejected alternative: 422 へ pin する案（→「非 2xx + denialReason enum」に restate）。SoD=403/state=409/input=422 の 4xx 細分を server contract に持つ案（→ enum で十分）。
  - nice-to-have（非拘束）: 将来 UI で「権限拒否」と「状態不整合」を視覚分離したくなったら、`denialReason` → 4xx の補助 mapping を **client 側で**導出できる。server contract には含めない。
- **D-6 notification 楽観の失敗 path**: markRead/markAllRead は冪等（再送で収束）。network 失敗時の UI rollback は **invariant 対象外**（server test で exercise できない＝falsifiable でないため matrix から除外）。背景再同期で整合する。

### Right-sizing notes

- **入れた（control を demonstrate するのに必須）**: dual-identity signed token（`X-Operator-Token` / `BOAI_SESSION_SECRET` で `session_operator_id` を確定、body `{ actorId }` は `effective_actor_id` のみ設定）、403/404 denial の明示化（silent no-op を可視 denial に、default 403 + IDOR のみ 404、`denialReason` enum）、zod `.strict()` による endpoint boundary 検証（未知 field reject = mass-assignment 防御）、append-only audit の保持（`session_operator_id` + `effective_actor_id` 両記録、deterministic `auditTs(seq)`）+ audit-less 集合の negative 固定（T-NO-AUDIT）、prior-state guard + identity-based SoD（自己承認 `isSelfApproval` / 裁定者一致 `escalation.to`）の server 移植、no-direct-patch + strict-body（T-NO-DIRECT-PATCH / T-STRICT-BODY）、**governance-boundary gate**（governance role は 24 mutation 全て reject = 唯一の role 認可、T-GOV-NO-MUTATE）、上記 T-* test 群。これらが無いと「四眼 SoD・propose/execute 分離・append-only audit・governance 閲覧専用」が falsifiable にならない。
- **入れない（production hardening = DEFECT として除外）**:
  - **per-action RBAC / operational role→endpoint 認可**: 過去版に 24 action × 3 operational role の role 認可表があったが、**live reducer に operational role guard が 1 件も無い**（`grep role` = `:56`,`:211` のみ）ため、これを server invariant に昇格するのは「既存 invariant の昇格」ではなく **net-new な role-permission engine の新設**になる。→ per-action role 認可は削除し、operational SoD は identity-based の 2 制約に統一（§B 前提注記）。demo の 3 固定 actor（`actors.ts:17-21`）は 1 role ずつゆえ identity 制約で四眼が成立する。**例外: governance-boundary gate は入れる**（READ-ONLY governance role が 24 mutation を mutate できない単一 boundary = SD-2、per-action RBAC engine ではなく 1 本の role check ゆえ right-sized）。
  - IdP / OAuth / JWT issuer、CSRF token、rate limit、監査の WORM/retention/改竄防止（`types.ts:9-11` が明言する通り session 操作記録 mock であり統制主張ではない）、audit 範囲の網羅拡張（D-3, 別 contract）。
  - HTTP status の 4xx 細分（D-5、default 403 + IDOR 404 + `denialReason` enum で十分）。
- **mock 境界は不変**: real customer data / real AI / real external 接続は無し（`CLAUDE.md` scope-out 維持）。server 化するのは **SoD/execute/audit の enforcement** のみ。
- **過剰設計シグナル（出たら STOP）**: action ごとに専用 service クラス / repository 抽象層 / DI コンテナ / role-permission engine を作り始めたら STOP。24 action は 1 reducer の switch（`reducer.ts:100-323`）で表現されており、server も「1 handler module + better-sqlite3 直 query + guard 関数（`isSelfApproval` 等を server へ移植）」で同 grain。新 framework 導入は re-right-size 対象。
- **client gate は authority でない**: `useCanApprove`/`useCanReverse`（`hooks.ts:135-164`、`by !== 'checker'` の role めいた gate を含む）・ApprovalsV2 の role hint（`ApprovalsV2.tsx:48-49`）の先回り disabled は UX 改善として残すが、**enforce の真実源は server の identity-based SoD + prior-state**。client gate を全削除しても server test が green であることが本 contract の合格条件。
